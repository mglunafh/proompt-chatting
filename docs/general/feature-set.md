# Feature set

IDs are allocated once and never renumbered or reused: a deleted entry leaves its
number vacant, and a feature that changes section keeps the prefix it was born
with. References carry both parts — `MSG-03 Message history` — so one that has
drifted is visible.

## Core messaging

- **MSG-01 Direct messages** — a 1:1 exchange between two users, or a user with themselves: the send frame is validated, written to Postgres, acknowledged to the sender with its server-assigned ID and timestamp, and fanned out to every live session of each participant. A message sent to a disconnected user is durable but not delivered until they reconnect. Body limits in [notes-validation.md](notes-validation.md); model decisions in [notes-core-messaging.md](notes-core-messaging.md).
- **MSG-02 Conversation list** — the conversations a user belongs to, ordered by last activity with the last message attached, fetched over REST at startup.
- **MSG-03 Message history** — scrollback fetched over REST in server-capped pages, keyed on the message ID rather than an offset so concurrent writes cannot shift a page.
- **MSG-04 Live connection** — one WebSocket per session carrying typed client and server frames defined in a module shared by both sides, with the protocol version checked once at the upgrade rather than on every frame. The server ticks a heartbeat carrying the user's head `change_seq` and a digest of the online set; the client's reply proves liveness, and the tick behind it re-checks the session row and refreshes its last use, so an expiry, a revocation and a demotion each reach an open socket within one interval. A rejected client frame comes back as a typed error frame rather than a close, since closing a misbehaving client returns it as a reconnect storm. Reconnect is client-driven with backoff, and only an application close code stops it. Framing, the heartbeat and the close codes in [notes-protocol.md](notes-protocol.md).
- **MSG-05 Offline catch-up** — on reconnect a client pages everything above the highest `change_seq` it has stored, one cursor covering inserts, edits, deletions and reactions; there is no queue and nothing expires. Cursor rules in [notes-core-messaging.md](notes-core-messaging.md).
- **MSG-06 Local history cache** — the client persists a contiguous top slice of history alongside its sync cursor, so a restart renders from disk and a reconnect fetches only what changed. The store is the client's business; the window's edges and the invariants around them are in [notes-client-cache.md](notes-client-cache.md).
- **MSG-07 Edit own message** — the sender amends their own message within 24 hours of sending; the body is revalidated, clients mark it edited, and the message keeps its ID, timestamp, and position. Window and edit rules in [notes-core-messaging.md](notes-core-messaging.md).
- **MSG-08 Delete own message** — the sender removes their own message at any time; the body is cleared and the row survives as a tombstone, so replies still resolve and offline clients learn of the deletion. A moderator removing someone else's message leaves the same tombstone.
- **MSG-09 Reply to a message** — a message may point at an earlier one in the same conversation and renders with a quoted line; replies stay flat and in chronological order.
- **MSG-10 Forward a message** — the body is copied into another conversation with `forwarded_from_id` recording the message it came from, and the copy is independent of the original thereafter. An attachment is cloned as a new record over the same blob, so no bytes move ([notes-attachments.md](notes-attachments.md)).
- **MSG-11 Emoji reactions** — a member adds or removes a reaction from a server-side allowlist, unique per message, user, and emoji. The allowlist carries an ASCII name per emoji, so clients accept `+1` rather than requiring emoji input, and terminal width stays predictable.
- **MSG-12 Mentions** — a message references members of its conversation, who are alerted and see the reference highlighted. The client composes the token `<@42>` where the sender picked a name and every client resolves it at render, so a rename reads correctly in old messages; the reference rides in the body rather than a frame of its own, and is recorded as a row per mentioned member so it can be tallied apart from the unread count. A token renders for any user but alerts only a current member, since a forward carries one into a conversation its subject is not in. Derivation in [notes-core-messaging.md](notes-core-messaging.md), alerting in [notes-notifications.md](notes-notifications.md).
- **MSG-13 Read cursor** — per-conversation read position for each member, feeding unread counts and "seen by". Semantics in [notes-core-messaging.md](notes-core-messaging.md).

## Authentication

- **AUTH-01 Opaque session tokens** — random strings looked up in a server-side `sessions` table rather than JWT, chosen for instant revocation; flows in [notes-authentication.md](notes-authentication.md), the table in [notes-db-schema.md](notes-db-schema.md).
- **AUTH-02 Registration** — accounts are created by redeeming an invite; flow in [notes-registration.md](notes-registration.md), the invite record in [notes-db-schema.md](notes-db-schema.md).
- **AUTH-03 Admin bootstrapping** — the first admin account is seeded at boot from a username variable and a mounted password secret, then retired once real admins exist; procedure and invariants in [notes-registration.md](notes-registration.md).
- **AUTH-04 Login** — verify the password, generate a 256-bit random token, insert a session row holding `hash(token)`, and return the raw token once.
- **AUTH-05 Request authentication** — `Authorization: Bearer <token>` on REST requests, looked up by SHA-256 hash; on WebSocket the token is validated once, at upgrade.
- **AUTH-06 Logout and revocation** — logout deletes the session row, logout-everywhere deletes every row for the user; ban disables the user, deletes their sessions, closes their live sockets via the in-memory connection registry, and revokes any invites of theirs with uses left.
- **AUTH-07 Account retirement** — a user disables their own account, confirmed with their current password: the same row change a ban makes, with sessions deleted, live sockets closed and outstanding invites revoked. Nothing of theirs is removed and an admin can re-enable it, so it is retirement rather than deletion, and the audit records it as its own action rather than as a ban. Rules in [notes-registration.md](notes-registration.md).
- **AUTH-08 Password change** — the user supplies their current password; the server verifies it, rehashes the new one, and revokes the user's other sessions.
- **AUTH-09 Password reset** — an admin issues a single-use, short-TTL reset token and shares it out-of-band, as with invites; redeeming it sets a new password and revokes all of the user's sessions. The token is stored hashed and redeemed by the same atomic conditional update as invites, with issuance and redemption both recorded in the audit chain. There is no public reset endpoint and no email dependency.
- **AUTH-10 Multi-session** — one row per login, so a user may hold concurrent sessions (console and TUI at once), each individually visible and killable.
- **AUTH-11 Token lifetime** — long-lived tokens with sliding expiry renewed on use, an absolute cap, and optional reaping of idle sessions. The heartbeat counts as use, so a session held open by a socket alone does not expire under it. Durations in [notes-authentication.md](notes-authentication.md).

## Users & presence

- **USR-01 User profile** — display name and bio, held as columns on the user row and set by the caller on themselves alone. Any authenticated user reads another's, since usernames and display names already render wherever two users share a conversation. Field rules in [notes-validation.md](notes-validation.md).
- **USR-02 Block user** — a member stops seeing another's messages: a direct send is refused by the server, and in a shared channel the client hides the body behind a collapsed marker. One-directional as a setting, bidirectional in effect within a DM, never announced to the blocked user and invisible to moderation — a refused send is generic, so what is hidden is the cause rather than the effect. Decisions in [notes-blocking.md](notes-blocking.md).
- **USR-03 Profile changes** — a username, display name or bio change is broadcast on the same channel and to the same audience as a presence frame, the setter's own sessions included, because every client caches the id-to-name mapping and would otherwise render the old name until it refetched. Rules in [notes-user-presence.md](notes-user-presence.md).
- **USR-04 Presence** — who is currently connected, per user rather than per client: the count of live sockets in the connection registry, held in memory and never persisted. Broadcast to every other connected session on the 0→1 and 1→0 edges only, with offline delayed by a short grace period so a reconnect does not flicker every roster. The offline frame carries `last_seen_at`. Model and broadcast rules in [notes-user-presence.md](notes-user-presence.md).
- **USR-05 Presence snapshot** — the full roster is pushed as the first frame after the WebSocket upgrade, captured by the same registry operation that adds the socket, and reconciled against a digest carried on the heartbeat.
- **USR-06 Declared status** — available, away or do not disturb, set by the user and never inferred, stored on the user row and sticky across disconnects. A label with no functional consequence: do not disturb suppresses nothing for now.
- **USR-07 Last seen** — `last_seen_at` on the user row, written when a user's last socket drops and repaired at startup from the newest session activity, since a hard kill runs no disconnect handler. Means last connected rather than last active.
- **USR-08 Typing indicators** — an ephemeral per-conversation signal, re-asserted by the sender while typing and expired by its receivers on a timer. There is no stop frame: a message clears its sender's indicator, and everything else falls to the expiry. Not sent in a server channel, where membership is every account. Intervals and the server-side floor in [notes-user-presence.md](notes-user-presence.md).

## Group / community management

- **COM-01 Group chats** — an invite-only multi-user conversation: any user creates one and adds registered users, and a user sees it only by holding a membership row, so there is no listing, no discovery and no join request. Messages stay flat, as in a direct message, with a reply quoting an earlier one without creating structure. A member added later sees the whole history; there is no per-member floor. Membership rules in [notes-community.md](notes-community.md).
- **COM-02 Channels** — a conversation a user finds and joins for themselves when public, or is entered by invitation when private, created by any user who becomes its owner. Membership adds writing, a read cursor and live delivery rather than access, so a non-member of a public channel reads it and nothing more; joining and reading both check for a kick, a member leaves at will, and one who joins later reads everything said before them. Membership rules in [notes-community.md](notes-community.md).
- **COM-03 Posts and comments** — two levels and never three: a post is a message with no parent, a comment is a message pointing at a post, and nothing hangs below a comment. Containment and quoting are separate pointers, so a comment may quote another without adding a level and a quote never points outside the post it renders in, and a deleted post survives as a tombstone so its comments stay addressable. Only posts count toward the unread number, with anything addressed to a member inside a comment thread reaching them through the mention tally. Pointers, the depth cap and the unread predicate in [notes-community.md](notes-community.md).
- **COM-04 Comment toggles** — comments are enabled or disabled per channel and per post, the channel setting being the default a post overrides, so a channel that disables them everywhere is a read-only announcement feed rather than a kind of its own. Rules in [notes-community.md](notes-community.md).
- **COM-05 Server channels** — a channel every account belongs to, with a membership row inserted at registration and backfilled for existing users when the channel is created, posted to by the server admins who already exist in the model, with any member free to comment where the channel enables them. The row is never deleted, so there is no leaving one and the per-conversation mute level is the only relief. Why membership is rows rather than implied in [notes-community.md](notes-community.md).

## Roles and moderation

- **MOD-01 Server roles** — an ordered role on the account: admin, mod or regular user, where each holds everything the one below it holds. Admins promote and demote, issue password reset tokens, create server channels and post in them, and issue invites without limit or use count; mods ban, unban and silence, and moderate public and server channels; a regular user holds none of it. Credential control stays with admins because a reset token can be redeemed to become the user it was issued for. Details in [notes-roles.md](notes-roles.md).
- **MOD-02 Conversation roles** — an ordered role on the membership row: owner, officer or member, one set shared by group chats and channels. The owner promotes, transfers ownership, archives, and decides whether members may post at top level; officers kick, silence, edit the name and description, delete others' messages, pin, add members and toggle comments; members read, write and leave. Server channels carry none, since membership is every account and write access comes from the server role.
- **MOD-03 Reach of a server role** — a mod or admin moderates public channels and server channels without being a member, and never reaches into a group chat or private channel. Abuse inside a private conversation is answered at the account level instead, which is what keeps private conversations private without leaving them unpoliceable.
- **MOD-04 Silence** — a member is made read-only without losing access, within one conversation or across the server. Held as a self-clearing deadline rather than a flag, so a timeout needs no second call to lift it. Owners and officers silence inside their own conversation, mods within any public or server channel or server-wide, where it reaches every conversation the user is in.
- **MOD-05 Kick** — a member is removed from a conversation and, in a public channel, kept from reading it or joining again, which is otherwise open to anyone. Owners and officers kick within their own conversation, as does a server role acting in a public channel. It holds until an owner or officer adds them back, returning them as a new member whose read position starts at the current end. Server channels have no kick; membership there cannot be removed.
- **MOD-06 Ban** — the strongest remedy and the only one that reaches a private conversation: the account is disabled, its sessions deleted, its live sockets closed and its outstanding invites revoked. Held by mods and admins. The mechanism is the revocation path described under Authentication.
- **MOD-07 Moderator deletion** — an owner or officer, or a server role acting in a public space, removes another member's message, leaving the same tombstone a sender-initiated delete leaves.
- **MOD-08 Archiving** — a conversation is retired rather than deleted: read-only, still readable by the members who were in it, out of the active list, and reversible. Owners archive and unarchive their own; an admin does it for a server channel; and a conversation left with no active member after a ban is archived by the server.
- **MOD-09 Protections** — banning and demoting require a strictly lower role in the same scope, reset issuance between admins is exempt since it escalates nothing, a holder may always act on themselves, and the server refuses to disable, demote or ban its last active admin. Every action at either scope lands in the audit log.

## Search & content

- **SRC-01 Message search** — a plain query string matched against the bodies of messages in the caller's conversations, returning a page of messages most recent first. Either `ILIKE` or a generated `tsvector` column can serve it, and the response is the same either way, so the mechanism can change without touching the wire. Routes and their trade-offs in [notes-search.md](notes-search.md).
- **SRC-02 Channel discovery** — public channels found by a query matched against their name and description, a lookup over conversation rows rather than message bodies, so a user can find a channel before belonging to it. Private channels are absent from the listing. Rules in [notes-community.md](notes-community.md).

## Attachments

- **ATT-01 File upload** — a member uploads a file over REST as a raw request body, with the original filename, declared type and an idempotency key in headers; the server answers with an id the sender then names in a message, and the WebSocket carries only that id. Bytes live on a local Docker volume keyed by the SHA-256 of their contents, so identical files occupy one blob and a retry resolves to the same path. Transport, storage and limits in [notes-attachments.md](notes-attachments.md).
- **ATT-02 Attachment lifecycle** — a record is claimed by its uploader for one conversation before any message references it, and bytes are written before the record and the record before the reference, so every interruption leaves something nothing points at rather than a pointer at something absent. States and ordering in [notes-attachments.md](notes-attachments.md).
- **ATT-03 Attachment sweep** — an hourly pass deleting records nothing has referenced for a day and then reclaiming any blob no record names, which is what makes the write ordering above affordable. Guards and the per-class passes in [notes-attachments.md](notes-attachments.md).
- **ATT-04 Attachment download** — `GET /attachments/{id}`, streamed, with `Range` support. Authorization is read off the record: an unreferenced one is readable by its uploader alone, a referenced one by any current member of the conversation it names, evaluated per request. Every refusal is a 404, the response is always `application/octet-stream` with `Content-Disposition: attachment` and `nosniff` rather than the stored type, and the `ETag` is the blob hash. Checks and headers in [notes-attachments.md](notes-attachments.md).

## Notifications & UX

- **NTF-01 Unread counts** — what a member has not read in each conversation, plus an aggregate badge across them and a separate tally for mentions. Counted from the read cursor, returned by the conversation list and recounted client-side between fetches. Definition, exclusions and computation in [notes-notifications.md](notes-notifications.md).
- **NTF-02 Conversation mute** — a per-member level on each conversation: alert on everything, alert only on mentions, or never, defaulting to everything and read on the send path from the membership row it already loads. A muted conversation leaves the unread badge while its own count stays accurate, and the mention tally survives the mentions-only level. Alerting policy only: every message is still delivered, stored and caught up on.

## Security

- **SEC-01 TLS transport** — Caddy terminates HTTPS and `wss://` in front of the server, obtaining and renewing Let's Encrypt certificates automatically; the server speaks plain HTTP on the internal Compose network. Stack in [notes-tech-stack.md](notes-tech-stack.md).
- **SEC-02 Credential rate limiting** — the routes that take a secret without a session: login, invite redemption and password-reset redemption. Failures are counted per source IP on all three and per username on login, which is the only one that has one, with progressive delay on the username dimension and a harder cap on the IP dimension; counters are in-memory and every failure is logged. Keyed on failures rather than attempts, so a user with a working password never meets it. Details in [notes-rate-limiting.md](notes-rate-limiting.md).
- **SEC-03 Secret management** — secrets are Docker Compose `secrets:` entries backed by one file per value, mounted read-only at `/run/secrets/<name>`, rather than environment variables. Consumers read the path from an `X_FILE` variable, the convention the official `postgres` and `grafana` images already use; the server supports both `X` and `X_FILE` for every secret it takes.
- **SEC-04 Interaction rate limiting** — a per-user token bucket per operation class: message sends, query endpoints, reactions and cursor advances, and attachment upload and download, enforced by Ktor's `RateLimit` plugin on REST routes and by hand inside the WebSocket read loop, which the plugin cannot see. Details in [notes-rate-limiting.md](notes-rate-limiting.md).
- **SEC-05 Name and label rules** — patterns, length caps and character rejections for usernames, display names, bios, group names, group descriptions, session labels and attachment filenames, the last stripped to a basename and kept as a display label that never reaches a filesystem path. Field rules in [notes-validation.md](notes-validation.md).
- **SEC-06 Password rules** — length bounds and a blocklist, with no character classes to satisfy; the one field whose raw value never reaches the database. Rules in [notes-validation.md](notes-validation.md).
- **SEC-07 Message body limits** — size and line caps, and rejection of the C0 and C1 control characters that carry terminal escape sequences. Limits in [notes-validation.md](notes-validation.md).
- **SEC-08 Transport caps** — WebSocket frame and HTTP body size, enforced before deserialization, which is what bounds the work an unparsed frame can cost. Values and enforcement point in [notes-validation.md](notes-validation.md).
- **SEC-09 Client-side sanitization** — a client renders untrusted text inertly rather than obeying it, since its untrusted input is the socket rather than the person typing. Client rules in [notes-validation.md](notes-validation.md).
- **SEC-10 Audit log** — a Postgres table recording who did what to whom and when: the bootstrap seed, promotion and demotion, invite issuance, redemption and revocation, password reset issuance and redemption, bans, unbans, disables and self-retirements, server-wide silences and their lifting, username renames, and conversation-scope moderation: kicks, silences, role changes, ownership transfers and automatic succession, metadata edits, archiving and moderator message deletion. A table rather than log lines, since the records carry foreign keys into `users` and are read alongside the rows they describe. Already depended on by the vouching chain in [notes-registration.md](notes-registration.md), by reset-token issuance above, and by renameable usernames in [notes-validation.md](notes-validation.md).

## Admin / ops

- **OPS-01 Health endpoint** — `GET /health`, a liveness probe for Docker Compose. No auth, no dependencies.
- **OPS-02 Structured logging** — every log line is a machine-readable record with its fields intact, rather than a sentence to be parsed back apart, so a failed login or a rejected frame can be found by field rather than by substring.
- **OPS-03 Metrics** — request rates, latencies and error counts exposed for scraping, so the server's behaviour under load is observable without reading logs. The throttle counters in [notes-rate-limiting.md](notes-rate-limiting.md) surface here.
- **OPS-04 Log aggregation** — logs from every container collected and queryable after the fact, without a log agent running beside the server.
- **OPS-05 Dashboards** — one view over the metrics and the logs together, which is where an operator looks first.
- **OPS-06 Backups** — cron'd `pg_dump` to local disk, starting once the database holds real data. No offsite copy.

## Nice-to-have

- **NH-01 Pinned messages** — a message flagged as pinned within its conversation, fetched with the conversation rather than pushed as a frame. Owners and officers pin, as does a server role acting in a public channel.
- **NH-02 Saved messages** — a conversation a user writes to alone, for notes to self and anything kept for later. It is the self-DM the canonical pair already permits, so nothing server-side is new. Bookmarking is forwarding into it with `forwarded_from_id` set, which is what makes the saved copy openable in its original discussion. The body is a snapshot: an edit to the original never reaches the copy, and a jump degrades to unavailable once the message is deleted or the reader loses access to its conversation, where a pointer would have lost the content too. Clients keep a table of saved source ids alone, never evicted, so the marker in the original conversation stays right even when the saved copy sits below the cache floor.
- **NH-03 Code block formatting** — monospace rendering of fenced code, client-side only.
- **NH-04 Markdown subset** — bold, italic and inline code rendered by the client; the server stores and sends the body untouched, marks and mention tokens alike.
- **NH-05 History export** — a conversation's history dumped to a file, under the same membership check as history paging, with mention tokens resolved to names on the way out. Cheap as a query and serialize; streaming a large one is what makes it bigger.
- **NH-06 Image thumbnails** — a smaller derived copy of an uploaded image, stored under `derived/<variant>/` keyed by its source blob's hash and named by the variant key on the attachment record. The layout reserves the space; what renders one in a terminal is the open question.
- **NH-07 Avatar** — a profile image, its bytes in the attachment store and its key on the user row rather than on an attachment record, which is conversation-scoped and would be swept a day after upload. The sweep then has to count avatar references before unlinking a blob. Blocked on the same question as thumbnails.
- **NH-08 Polls** — create, vote and close within a conversation, held in a table of its own.
- **NH-09 Two-factor authentication** — opt-in per user; an admin's password reset clears any enrolled factor, and enrollment, disable and recovery-code use join the audit chain. Storage, crypto and thresholds in [notes-totp.md](notes-totp.md).
  - **Verification (TOTP)** — RFC 6238, 30-second step, 6 digits, verified server-side with `HmacSHA1`; adjacent time steps are accepted for clock skew and the last-used step is recorded so a code cannot be replayed. A password check alone issues no session row — login returns a "needs second factor" state, and the session is created only once a code verifies.
  - **TOTP enrollment** — the server generates the secret and presents it as a base32 key typed into an authenticator app by hand; terminal QR rendering is deferred client-only polish. Activation requires one live code, so a mistyped secret cannot lock the user out.
  - **Recovery codes** — ten single-use codes, stored hashed and shown once at enrollment; the only self-service way back in after a lost device, since there is no email in the model.
