# Step 2 tasks

## Setup

- **W-01 Build scaffolding** — a `shared` module under `:step2-durable` alongside its `server` and `client`, and catalog entries for the Ktor server and client on the CIO engine with their WebSocket and JSON plugins, kotlinx-coroutines, kotlinx.serialization, Exposed, the Postgres driver, HikariCP, Flyway, password4j, Caffeine, Clikt, Logback, ktlint, JUnit 5, coroutines-test, Testcontainers and MockK. The `application` plugin on both the client and the server, each with an entry point. Carries no feature.
- **W-02 Postgres and Compose** — a `docker-compose.yml` with a Postgres service, a named volume and a health check, the server's connection settings read from environment variables, and every secret taken as both `X` and `X_FILE` so a mounted file works where a variable does. The pool opened once at boot and closed on shutdown. Carries no feature.
- **W-03 Schema and migrations** — Flyway on the classpath and run at startup before anything reads a table, and the first migration: `users`, `invites`, `sessions`, `conversations`, `conversation_members`, `messages`. `bigserial` message ids, `NOT NULL` sender, server-assigned `created_at`, the unique index on `(direct_lo, direct_hi) WHERE kind = 'direct'`, and the unique index on `(sender_id, client_msg_id)`. Carries no feature.
- **W-04 Database test harness** — a Testcontainers Postgres shared across the suite, migrations run once against it, and per-test isolation by rolling back rather than by truncating. The fixture that boots the server under `testApplication` against that container, so every later task tests against a real database. Carries no feature.
- **W-05 Server entry point and health** — the Ktor application built from the configuration W-31 resolves, its boot report emitted through the structured startup logging, and `GET /health` answering without auth and without touching the database. The first thing that runs end to end under Compose. OPS-01.
- **W-31 Server configuration** — the setting registry as an enum carrying both spellings, the type, the default and whether the value is a secret, and the resolver over the four sources in the order [notes-configuration.md](../general/notes-configuration.md) fixes. A source answers a setting in either form and answering wins outright; both forms within one source is the only ambiguity. Failures are collected rather than thrown at the first, and the boot report names the source behind each value with secrets redacted. Replaces the string-keyed reader W-02 left behind. OPS-07.

## Shared and pure

- **W-06 Protocol module** — the client and server frame hierarchies as sealed types with their serializers, the version constant checked at the upgrade, the transport and body caps, the close codes `4401`, `4403` and `4409`, and `client_msg_id` as the ack correlation key. The server rejects unknown keys and the client ignores them, so the asymmetry is a serializer configuration rather than a convention. Tested by JSON round-trip and by a decode of a frame carrying an unknown key against each side. MSG-04, SEC-07, SEC-08.
- **W-07 Validation** — pure functions for the username pattern and length cap, the password length bounds and blocklist, and the message body size, line count and C0/C1 control-character rules. Table-driven tests. SEC-05, SEC-06, SEC-07.

## Accounts

- **W-08 Users and passwords** — the `users` table access: insert, find by username, find by id, and the disabled flag; Argon2id hashing and verification through password4j, with a rehash when a row was written under older parameters. Verification timed on a missing user as on a present one, so the route cannot be used to enumerate names. AUTH-04.
- **W-09 Sessions store** — insert a session holding `hash(token)` with an absolute `expires_at`, look one up by token hash rejecting an expired row, refresh `last_used_at`, delete by id and delete every row for a user. Concurrent inserts for one user tested, since multi-session is the property rather than an accident. AUTH-01, AUTH-10, AUTH-11.
- **W-10 Invites and account creation** — issue an invite storing `hash(token)` with a TTL and returning the raw value once, and redeem it by a single conditional `UPDATE ... WHERE token_hash = ? AND used_at IS NULL AND expires_at > now()` acting on rows-affected, creating the account in the same transaction. Never read-then-write. Tested with two concurrent redemptions of one token, exactly one of which may win. AUTH-02.
- **W-11 Bootstrap admin** — a boot-time seed reading `BOOTSTRAP_ADMIN_USERNAME` and `BOOTSTRAP_ADMIN_PASSWORD_FILE`, inserting only when that identity is absent rather than when the table is empty, so a retired seed is not resurrected and the credential never updates an existing row. Tested by booting twice, and by booting again after the seeded account is disabled. AUTH-03.
- **W-12 REST authentication** — the `Authorization: Bearer <token>` path: hash, look up, bind the request to a user, and reject with `401` for unknown or expired and `403` for disabled. Installed as one Ktor authentication provider every protected route names. AUTH-05.
- **W-13 Auth routes** — `POST /register` redeeming an invite, `POST /login` returning the raw token once, `POST /logout` and `POST /logout-all`, and the admin-only invite issuance endpoint. Passwords validated before hashing, and no route ever returns a token or a hash it did not just mint. AUTH-02, AUTH-04, AUTH-06.
- **W-14 Credential rate limiting** — in-memory Caffeine counters over login and invite redemption: per source IP on both, per username on login, with progressive delay on the username dimension and a harder cap on the IP dimension. Counted on failures rather than attempts, and every failure logged as a structured record. Tested with virtual time, so the delay is asserted rather than waited on. SEC-02.
- **W-15 Account disable** — the admin route setting the flag, deleting the account's sessions and revoking its unredeemed invites in one transaction, the re-enable beside it, and the guard refusing to disable the last active admin. The socket half is W-19. MOD-06.

## The live connection

- **W-16 Connection registry** — a map of session id to socket, one socket each, with the per-user count derived from it; insert capturing the presence snapshot in the same operation, removal, a lookup by user for fan-out, and the displacement rule where an upgrade for a session that already holds a socket registers the new one and then closes the old one with `4409`, in that order, so the user's count never touches zero. Tested without Ktor, concurrent inserts and a displacement race included. AUTH-01, USR-04, USR-05.
- **W-17 Upgrade and read loop** — the WebSocket route: validate the token once, check the protocol version, register or refuse with `401`, `403`, `426` or `429`, run the read loop, and answer a rejected client frame with a typed error frame rather than a close. MSG-04, AUTH-05.
- **W-18 Heartbeat and expiry** — the server tick and the client reply, a close after consecutive missed replies, and the work behind each tick: re-read the session row, close the socket if it is gone or expired, and refresh `last_used_at`. The reply is exempt from any interaction limit. Tested on virtual time against a row deleted and a row expired under an open socket. MSG-04, AUTH-11.
- **W-19 Revocation reach** — every revoke path closing its sockets through the registry: logout with `4401`, logout-everywhere across the user's sessions, and disable with `4403`. A socket authenticates once at the upgrade and never revisits the table, so this is what makes revocation instant rather than eventual. Tested by revoking against a live in-process socket and asserting the code it sees. AUTH-06, MOD-06.

## Presence

- **W-20 Presence edges and grace** — online broadcast on 0→1 and offline on 1→0, to every other connected session and never to the user's own, with the offline frame delayed by a coroutine `Job` per user that a reconnect cancels outright. Session churn between the edges emits nothing. Tested on virtual time: a second socket is silent, a reconnect inside the window cancels, one outside it fires. USR-04.
- **W-21 Presence snapshot** — the roster as the first frame after the upgrade, taken from the registry operation that added the socket, reporting broadcast state rather than the raw count so a user inside their grace window still reads as online. Entries carry a user id and username. Tested with three in-process clients, one of them mid-grace. USR-05.
- **W-22 Last seen** — `last_seen_at` written when a user's socket count reaches zero, stamped then rather than when the grace expires, and the boot repair raising each user's value to the newest `last_used_at` across their sessions where that is later. Tested by killing the server with a socket open and asserting the repair on the next boot. USR-07.

## Messaging

- **W-23 Conversation and message store** — resolve-or-create the `direct` conversation for a canonical pair with its membership rows, insert a message returning the existing row when `(sender_id, client_msg_id)` already exists, page history `before` an id under a server cap, and list a user's conversations ordered by last activity with the last message and the members attached. Every read takes a membership check. Tested with concurrent first-sends between one pair, which must not fork the history. MSG-01, MSG-02, MSG-03.
- **W-24 Send path and fan-out** — validate the body, persist, then ack the sender with the server-assigned id and timestamp and fan out to every live session of both participants, the sender's own included. Persist before delivering, so anything a client has seen is re-fetchable. Tested with the recipient connected twice and with the recipient absent. MSG-01.
- **W-25 REST read routes** — `GET /conversations` and `GET /conversations/{id}/messages`, both behind W-12 and both refusing a non-member the same way they refuse a missing row. MSG-02, MSG-03.

## Client

- **W-26 Client token store** — the token persisted to a file under the user's configuration directory, created with owner-only permissions and rewritten atomically, loaded at startup and discarded on `4401`. ST2-01.
- **W-27 Client account commands** — `register`, `login` and `logout` as Clikt subcommands, with passwords prompted and read without echo, never accepted as an option or an environment variable, and typed twice at registration. AUTH-02, AUTH-04, ST2-02.
- **W-28 Client connection and reconnect** — connect with the stored token, concurrent send and receive loops, exponential backoff with jitter on a drop, and a halt only on a close code the client knows: `4401` discards the token and asks for credentials, `4403` discards it and stops, `4409` keeps it and offers a manual reconnect. An unrecognized code, a missing one, `1001` and `1006` all mean retry. Tested against a server that closes with each. MSG-04.
- **W-29 Client rendering** — inert rendering of message bodies and usernames on the way to the terminal, covering history pages and conversation rows as well as live frames, plus the id-to-name map built from the presence snapshot and the presence frames after it. SEC-09.
- **W-30 Client commands** — `@name` addressing a recipient, and the `/` commands beside it: `/help`, `/exit`, `/list` printing the conversation list, `/history` paging the current conversation backwards, `/who` printing the roster. An unrecognized `/word` refused as a command. Table-driven tests on the parse, and the README. ST2-03.
